信息隔离的双向渲染（Information-Isolated Dual-Control Rendering）

优先级：P0 模块：DialogueGenerator & 在线双路径评测器 文献对标：τ²-Bench (2506.07982) / UserProxyBench (2609.38043) 状态：待实施 (Planned)
1. 现状痛点与改造动机（为什么从“单模型全知写剧本”升级为“信息隔离双向渲染”？）

❌ 现状痛点：单模型全知视角剧本渲染 (Omniscient Single-LLM Script Rendering)

  • User / Agent 视野未物理隔离：在 cross_memory_data/src/generation/dialogue_generator.py 中，同一个 LLM 同时接收完整的 target_params（含待测答案槽位）与 snapshot_before（历史记忆状态），一次性生成多轮 User 和 Agent 台词。
  • 首轮过早信息泄露（Premature Disclosure）风险：由于渲染 User Turn 1 时模型脑中装着最终答案（如 resolution=1080p, duration=180min），即便在 Prompt 中写满“严禁在第1轮提及画质与时长”，LLM 仍有概率在口语润色时顺嘴漏出答案或同义提示词（对应 UserProxyBench 实测高达 24.4% 的用户模拟器违规率）。
  • 慢路径与快路径无法在线动态切换：静态 JSONL 台词写死了轮数。在评测 memory_system 时，若被测 Agent 在本应走快路径的场次发起了追问（或反之），静态录好的 Turn 2 User 台词无法根据 Agent 的真实回复动态接话。

✅ 目标机制：信息隔离的双向渲染 (Information-Isolated Dual-Control Rendering)

  • 物理级输入裁剪（Input-Level Information Isolation）：将会话状态显式拆分为 用户私有状态表（User Private State） 与 助手可见记忆状态（Agent Observable Memory State），从输入字典层面物理剥离对方不该看见的字段。
  • Turn 1 用户盲盒表达约束：生成或模拟 User Turn 1 时，输入中物理剔除本轮待通过记忆补全或待 Turn 2 澄清才揭晓的槽位，只传入本轮允许暴露的最小业务锚点与个性化表述映射（expression），从根源上令首轮泄露率降为 0%。
  • 支持快/慢双路径自适应对弈（Dual-Path Reactive Loop）：模拟用户持有条件反馈表（Conditional Response Policy）——若 Agent 在 Turn 1 已通过记忆补齐槽位并提议正确方案，User 直接确认闭环（快路径 2 轮）；若 Agent 发起追问或未触发经验偏移，User 按私有状态表在 Turn 2 补充/纠偏（慢路径 2~3 轮）。

👤 用户侧受控视图 (User Private State)

驱动 User Turn Renderer / Simulator：

  • Turn 1 显式暴露槽位 (exposed_slots_t1)：仅含当前场景最小锚点（如 env="奥体中心"、代称 "开播保障"）。
  • Turn 2+ 待揭晓私有槽位 (latent_private_slots)：仅在 Agent 追问、消歧或未命中经验时才允许在 Turn 2 披露（如 "提前30分钟预热"、或指明选定哪笔历史工单）。
  • 人物语言风格 (speech_style)：语气、口头禅。
🚫 物理屏蔽：Turn 1 严禁传入待由记忆补全的 resolution / rtt / duration 真值，亦不可见 Agent 内部数据库结构。

🛡️ 双轨保真度与防泄漏守卫 (Fidelity & Leakage Gate)

基于 UserProxyBench 与确定性状态校验：

  • Gate 1：Turn 1 过早泄露静态拦截（Premature Disclosure Check）：扫描 Turn 1 User Utterance，断言其中绝不包含被标记为 memory_filled 或 turn2_disambiguated 的目标槽位字面量及数值。
  • Gate 2：快/慢路径动作合规校验：
    • 快路径场次：Agent Turn 1 必须完成记忆槽位展开并发起 Confirm_Slot；
    • 慢路径场次：Agent Turn 1 必须发起 Request_Slot / Request_Disambiguation，由 User Turn 2 揭晓私有槽位。
✅ 终态判定：比对对话收敛后的最终成交槽位 final_slots 与 ground_truth_slots 是否 100% 一致。
3. 真实样本举例：同一套状态表如何同时驱动“离线防泄密渲染”与“快/慢双路径交互”？

以 USER_001（户外赛事摄影师） 的两个典型会话为例，展示物理拆分后的输入字典与逐轮交互过程：

输入给 User 渲染器的受控字典（user_private_view） 

{
  "session_id": "S-08_implicit_reuse",
  "turn_1_allowed_input": {
    "scenario_env": "常规周期保障现场",
    "exposed_expressions": ["午间例行", "老规矩"],
    "exposed_anchors": {"application": "抖音", "service": "开直播"},
    "strictly_hidden_in_turn_1": ["12:00~14:00", "120min", "1080p", "50ms"]
  },
  "turn_2_conditional_policy": {
    "if_agent_proposes": {
      "application_name": "抖音",
      "service_name": "开直播",
      "start_window": "12:00~14:00",
      "duration": "120min",
      "resolution": "1080p",
      "rtt": "50ms"
    },
    "then_user_action": "Confirm_Slot (简短确认开通)",
    "else_if_agent_asks_missing_slot": "按 ground_truth 补充缺失项并记录 Agent 记忆召回失败"
  }
}

输入给 Agent 渲染器 / 被测系统的受控字典（agent_observable_view） 

{
  "session_id": "S-08_implicit_reuse",
  "user_turn_1_utterance": "今天在常规周期保障现场，按‘午间例行’的时间，老规矩用抖音做开直播，帮我把保障开上。",
  "retrieved_memory_snapshot": {
    "periodic_preference": [
      {"window_label": "午间例行", "time_range": "12:00-14:00", "app": "抖音", "service": "开直播", "status": "active", "retention": 0.94}
    ],
    "preferred_value": [
      {"app": "抖音", "service": "开直播", "resolution": "1080p", "rtt": "50ms", "duration": "120min", "status": "reinforced", "retention": 0.96}
    ]
  },
  "ground_truth_slots": "<REDACTED_FROM_AGENT>"
}
交互场景类型 Turn 1 User（仅见 turn_1_allowed_input） Turn 1 Agent（仅见 Turn 1 User + 记忆快照） Turn 2 User & 闭环结果（受 turn_2_policy 约束）
场景 A：事实/经验快路径复用
（记忆库已含生效记录）		 “今天在常规周期保障现场，按‘午间例行’的时间，老规矩用抖音开直播，把保障开上。”
✔ 物理未传入 1080p/50ms/120min，绝对零泄露		 检索命中 periodic_preference 与 preferred_value，主动展开槽位：
“收到，按您‘午间例行’的老规矩，为您预约今日 12:00至14:00（持续120分钟） 的抖音开直播保障，画质 1080p、时延 50ms以内，请确认是否开通？”		 匹配 if_agent_proposes 成功：
User：“对，就按这个老规矩直接开通吧。”
Agent：“已为您开通本次保障。”（快路径 2 轮闭环）
场景 B：工作记忆多单冲突 / 经验首次沉淀慢路径
（记忆库存在 2 笔同场馆不同规格工单，或首次遇大型场馆）		 “今天15:00到17:00去会展中心用抖音开直播，按我之前在会展中心办过的那单规格来。”
✔ Turn 1 隐藏具体选哪笔历史单据		 检索 working_record 发现会展中心有两笔历史工单（上周五 1080p/50ms vs. 上周二 720p/100ms），触发慢路径消歧：
“查到您在会展中心有两笔历史保障单：一笔是上周五的 1080p/50ms，另一笔是上周二的 720p/100ms，请问本次按哪一笔规格办理？”		 匹配 Request_Disambiguation，启用 turn_2_latent_slots：
User：“按最近上周五那次 1080p、50ms 的规格来。”
Agent 汇总确认后在第 3 轮完成开通，并沉淀消歧经验（慢路径 3 轮闭环）。
4. 分步工程落地清单（Actionable Implementation Steps）
  • 1
    Step 1（数据侧 cross_memory_data）：重构视图投影函数 build_isolated_views(s_plan, snapshot_before)
    在 src/generation/dialogue_generator.py 中，将原本直接传给 Prompt 的全量 s_plan 拆分为 user_turn1_view（物理剥离待由记忆补全的 resolution / rtt / duration / target_app 字段）、agent_view（仅注入 snapshot_before 生效记忆卡）与 user_turn2_view（仅在 Turn 2 传入确认或纠偏参数）。
  • 2
    Step 2（校验侧 cross_memory_data）：新增 PrematureDisclosureValidator（首轮过早信息泄露拦截器）
    在 src/validation/qc_validator.py（及 dialogue_generator.py 的 _validate_rendered_turns）中，借鉴 UserProxyBench (2609.38043) 的 UFS 指标，针对所有复用/强化/消歧会话，静态扫描 turns[0]["user_utterance"]：凡出现本应由记忆检索或 Turn 2 澄清才产生的槽位字面量，直接判定为 Premature Disclosure 并触发单会话重生成。
  • 3
    Step 3（评测侧 memory_system）：构建轻量级 EnvironmentCoupledUserSimulator 支持快/慢双路径在线对弈评测
    在 memory_system/scripts/ 下新增双向控制在线评测脚本：被测 Agent 每轮调用真实的 MemorySystem.search() 获取记忆上下文并生成回复；UserSimulator 仅持有当前测试样本的 user_private_view，根据被测 Agent 在 Turn 1 是“直接给出完整参数（快路径）”还是“发起反问澄清（慢路径）”动态生成 Turn 2 回复，最终以双方收敛后的结构化订单槽位比对 Ground-Truth 计算端到端通过率。
